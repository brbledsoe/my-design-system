# Agent guidance for creating and updating components

_Research date: 2026-11-25._

Start with a short root `AGENTS.md` that routes component work to the catalog contract, the nearest maintained implementation and the relevant verification. Keep the examples runnable. Give repeated workflow steps a component skill if agents still miss them, and let a formatter handle mechanical style when the project adopts one.

## What the evidence supports

- **Repository instructions can steer behavior.** Gloaguen et al. found that agents generally followed context-file instructions and did more exploration and testing. In their mostly Python task-resolution benchmarks, the estimated success changes for generated and developer-authored files were small and statistically insignificant. Inference cost rose by over 20% on average. A separate 124-PR Codex study reported about 29% lower median runtime and 17% lower median output tokens with existing instruction files. It used a manual sanity check on a subset in place of a full correctness evaluation. These studies measure different outcomes in different setups. [Gloaguen et al., v3](https://arxiv.org/html/2602.11988v3) · [Lulla et al., v2](https://arxiv.org/html/2601.20404v2)
- **Nearby examples can steer implementation choices, and explicit priorities help when precedent conflicts with the task.** In a controlled study, agents followed repository precedent over model defaults in 359 of 360 trials, with example placement materially affecting adoption. When the task required departing from established precedent, a written priority rule achieved joint functional success and target adoption in 59 of 60 trials versus 38 of 60 with an example alone in that comparison. The tested changes concerned API implementation choices. For this repository, the case for a pointer to a maintained component is an inference. [Precedent or Intent?](https://arxiv.org/html/2610.38244v1)
- **Stale guidance can waste work even when the patch succeeds.** A controlled study of three instructions found that agents often followed an outdated component-addition procedure when it was relevant. The study detected additional tool calls for one model on the stale test command. Correcting stale instructions removed operations on the obsolete paths. This favors deriving commands and wiring from maintained files. [When Instruction Files Go Stale](https://arxiv.org/html/2611.09802v1)

## Candidate root guidance

> For component work, use the README's catalog contract and the nearest maintained implementation in the target package. Define the public API, states, interactions and accessibility in the component's consuming example. Keep platform implementations in their own packages and use shared tokens for shared design values. Use ERIQ as reference material for explicit ERIQ work. Verify consumer-facing changes using the compatibility guide and the packed-consumer checks.

Treat usability as part of implementation. Decide semantics, keyboard or touch behavior, focus, accessible names and relevant states before writing the component. Once the public example works, use a UI polish skill when the task calls for visual or interaction refinements and recheck affected behavior. For Box, a useful contract is the chosen semantic element, its accessible name where appropriate and token-backed padding. Button and Switch provide precedents for controls with state and input. [Box reference](../../apps/vue-pilot/box.html) · [Notification preferences pattern](../patterns/notification-preferences.md) · [Compatibility guide](../reference/compatibility.md)

If the team wants to test the guidance, try the same small component addition and an update in fresh sessions with the current setup and with the short root guidance. Compare public import, example coverage, behavior and accessibility, verification, formatting, and review corrections. Track time or tokens separately from correctness. The published studies give reasons to try this setup, with its results still to be measured here.
